# 密钥与数据恢复声明 / Keys and data recovery notice

## 中文

**主密钥一旦损坏或丢失，已加密的数据将永久无法恢复。任何人都无法恢复，包括开发者。** 这不是技术能力的问题，而是加密本身的设计：没有密钥，就没有数据。

**请妥善保管您的主密钥，以及部署软件的电脑和服务器。**

### 1. 加密方式

- 业务数据、AI 服务凭据和对话记录以 AES-256-GCM 加密后保存。每个实例只有一把 32 字节的随机主密钥，每份密文都绑定所属工作室和用途。
- 软件没有后门，没有备用密钥，也没有找回功能。开发者不保存、也接触不到任何实例的主密钥。256 位随机密钥无法靠穷举猜出。
- 账户密码不以原文保存：每个账户使用独立的随机盐，经 scrypt 计算后只保存结果。密码同样无法找回，但可以由管理员重置；主密钥不能重置。

### 2. 主密钥保存在哪里

| | 桌面版 | 服务器版 |
| --- | --- | --- |
| 生成方式 | 首次启动时自动生成，界面中不显示 | 部署者生成，填入 `cloud/.env` 的 `STUDIO_MASTER_KEY` |
| 保存位置 | `%APPDATA%\Limet Otus Studio\vault-key.dpapi`，由 Windows 数据保护接口（DPAPI）加密，只能在同一台电脑、同一个 Windows 用户下解开 | `cloud/.env`，以及部署者另行保存的副本 |

### 3. 以下情况会导致数据无法恢复

- **硬件**：硬盘损坏、电脑丢失、被盗或报废。
- **系统**：重装 Windows、重建或删除 Windows 用户、管理员强制重置该 Windows 用户的密码、系统数据保护功能损坏。
- **操作**：删除或改动 `vault-key.dpapi`；服务器版丢失 `cloud/.env` 且没有另行保存主密钥；更换了主密钥。
- **恢复**：用与数据不匹配的主密钥恢复服务器备份。

### 4. 备份能做什么、不能做什么

- **导出备份（JSON）**：业务配置 → 数据管理 → 备份与恢复。导出文件**不加密**，不依赖主密钥，可在新电脑或新实例中导入。这是桌面版在密钥丢失后唯一能用的恢复办法。文件包含客户资料，请当作敏感资料保管；不包含成员账户和接口密钥，导入后需要重新设置。
- **桌面版 Git 备份**：用**同一把主密钥**加密。主密钥丢失后，远端的 Git 备份同样无法解开。它只能在原电脑、原 Windows 用户仍可使用时，帮助找回误删或改错的数据。
- **服务器版数据库备份**：只能用原主密钥恢复。

### 5. 部署者与使用者必须做的事

1. **定期导出 JSON 备份**，保存到与本机分开的地方，例如加密的移动硬盘。重要变更前后各导出一次。
2. **服务器版的主密钥离线另存**，例如保存在离线的密码管理器中，并与服务器和备份分开存放；知道主密钥的人越少越好。
3. **做好物理保护**：设备放在可控的场所，设置开机密码与屏幕锁定，开启整盘加密，留意硬盘健康状况，不随意交给他人维修或保管。
4. **定期演练恢复**：在另一台电脑或独立环境中导入备份，确认订单、工单和配置都能读出。从来没有成功恢复过的备份，不能算作备份。
5. **重装系统、换电脑、重建用户之前**，先导出备份并确认导入可用。

## English

**If the master key is damaged or lost, the encrypted data is gone for good. Nobody can recover it, the developers included.** This is not a matter of skill. It is what encryption means: no key, no data.

**Keep your master key safe, and look after the computers and servers the software runs on.**

### 1. How data is encrypted

- Business data, AI service credentials and conversations are stored encrypted with AES-256-GCM. Each instance has a single random 32-byte master key, and every ciphertext is bound to its studio and purpose.
- There is no back door, no spare key and no recovery feature. The developers never hold or see any instance's master key. A random 256-bit key cannot be guessed by brute force.
- Account passwords are never stored as such: each account has its own random salt, and only the scrypt result is kept. Passwords cannot be recovered either, but an administrator can reset them. The master key cannot be reset.

### 2. Where the master key is kept

| | Desktop | Server |
| --- | --- | --- |
| Created | Generated automatically on first launch; never shown | Generated by the deployer and set as `STUDIO_MASTER_KEY` in `cloud/.env` |
| Kept in | `%APPDATA%\Limet Otus Studio\vault-key.dpapi`, encrypted with the Windows Data Protection API (DPAPI); it can only be unlocked on the same computer by the same Windows user | `cloud/.env`, plus the copy the deployer keeps elsewhere |

### 3. What makes data unrecoverable

- **Hardware**: a failed disk, or a lost, stolen or retired computer.
- **System**: reinstalling Windows, recreating or deleting the Windows user, an administrator forcing a password reset for that user, or a damaged Windows data protection store.
- **Operations**: deleting or changing `vault-key.dpapi`; losing `cloud/.env` on a server without a separate copy of the key; replacing the master key.
- **Restoring**: restoring a server backup with a master key that does not match it.

### 4. What backups can and cannot do

- **Export backup (JSON)**, under Business configuration → Data management → Backup and restore. The file is **not encrypted** and does not depend on the master key, so it can be imported on a new computer or instance. On the desktop it is the only way back after the key is lost. It contains customer details, so treat it as sensitive. It excludes member accounts and API keys, which must be set up again after import.
- **Desktop Git backup**: encrypted with **the same master key**. Once the key is lost, the remote Git backup cannot be opened either. It only helps recover deleted or mistaken changes while the original computer and Windows user still work.
- **Server database backups**: can only be restored with the original master key.

### 5. What deployers and users must do

1. **Export a JSON backup regularly** and keep it away from the computer, for example on an encrypted external drive. Export before and after major changes.
2. **On a server, keep the master key offline**, for example in an offline password manager, separate from the server and from the backups. Keep the number of people who know it small.
3. **Protect the hardware**: keep devices in a controlled place, use a sign-in password and screen lock, turn on full-disk encryption, watch disk health, and do not hand devices to others for repair or safekeeping without care.
4. **Rehearse a restore regularly**: import a backup on another computer or in a separate environment and confirm that orders, tasks and configuration read back. A backup that has never been restored is not a backup.
5. **Before reinstalling Windows, changing computers or recreating a user**, export a backup and confirm that it imports.
