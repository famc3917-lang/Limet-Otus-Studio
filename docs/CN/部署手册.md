# 观隅鸮馆 V3.0.0 部署手册

本软件开发使用了 AI 辅助。

本手册面向负责安装和维护的人员，说明两种使用方式：

- **桌面版**：在一台 Windows 电脑上安装使用，数据保存在本机。
- **服务器版**：用 Docker Compose 在 Linux 服务器上部署，团队成员通过浏览器访问。

本手册描述的是推荐做法。软件按现状提供，不保证数据的保密性、完整性、持续可用或可恢复，也不保证金额计算准确；部署方须根据自身情况评估风险并自行承担运维责任。请先阅读[现状与责任说明](../../NOTICE-AS-IS.md)。

> **最常见的问题：服务器版必须通过 HTTPS 访问。**
> 服务器模式下，登录会话 Cookie 带有 `Secure` 标记，浏览器只会在 HTTPS 连接中保存它。如果用 `http://` 访问服务器的 IP 或域名，登录请求看起来成功，但浏览器不会保存会话，页面会一直回到登录界面。请按第 3 节配置域名与证书，不要为了“先能用”而关闭这一机制。只有在服务器本机用 `http://localhost` 访问时，浏览器才会接受该 Cookie。

## 1. 配置要求

以下数字由各组件的实际资源设置推算，**未经容量实测**。人数多、订单量大或同时使用语音时，请在上线前用接近实际的数据做压力测试。

### 1.1 桌面版（Windows）

| 项目 | 最低可运行 | 推荐 |
| --- | --- | --- |
| 系统 | Windows 10 1803 或更新的 64 位版本 | Windows 11 64 位 |
| CPU | 4 线程 | 6 核 12 线程以上 |
| 内存 | 8 GB（不使用语音合成） | 16 GB（使用语音合成时的基线） |
| 磁盘 | 2 GB 可用（程序约 0.9 GB 加数据） | SSD，10 GB 以上可用（语音合成运行时与模型约 5–6 GB） |
| GPU | 不需要 | 可选：NVIDIA 显卡，显存 4 GB 以上，驱动 531 或更新，用于加速语音合成 |
| 网络 | 使用 AI、天气或首次安装语音时需要 | 稳定宽带 |

说明：

- 不用语音功能时，软件对 CPU 和内存要求不高，GPU 完全不需要。
- 语音识别（SenseVoiceSmall INT8）用 CPU 2 线程，模型约 230 MB。
- 语音合成（CosyVoice-300M-SFT）用 CPU 4 线程，推理进程约占 5 GB 内存；检测到符合条件的 NVIDIA 显卡时自动使用 CUDA，否则用 CPU，速度明显较慢。
- 识别与合成共用一个推理名额，同一时间只运行一种，空闲 90 秒后释放。

### 1.2 服务器版（Linux）

以下按个人或超小型工作室的日常使用估算，未做多人并发压力测试。

| 项目 | 最低可运行 | 推荐 |
| --- | --- | --- |
| 系统 | 仍在维护期内的 Ubuntu LTS，64 位（x86_64） | Ubuntu 24.04 LTS |
| CPU | 2 vCPU | 4 vCPU 以上 |
| 内存 | 4 GB | 8 GB 以上（服务器启用语音识别时再加 1 GB） |
| 磁盘 | 20 GB SSD | 50 GB 以上 SSD，另有独立的备份存储 |
| GPU | 不需要 | 不需要（服务器版不含语音合成） |
| 网络 | 公网 IP 或内网固定地址，开放 80/443 | 同左，另配监控与告警 |
| 其他 | 一个域名（或内网 DNS 名称）与有效证书 | 同左 |

- 服务器版由四个容器组成：PostgreSQL、Next 页面、独立 API、Caddy 反向代理。
- **服务器版不提供语音合成。** 语音识别需按第 6 节另行放入模型。
- 桌面悬浮球、托盘和本机设备接入只在桌面版提供。

## 2. 桌面版安装

1. 选择安装版 `LimetOtusStudio-Setup-3.0.0-x64.exe` 或便携版 `LimetOtusStudio-Portable-3.0.0-x64.exe`（免安装）。安装版为当前用户安装，不需要管理员权限；默认位置为 `%LOCALAPPDATA%\Programs\LimetOtusStudio`，可在安装时更改；会创建开始菜单与桌面快捷方式，并在“设置 › 应用”中登记卸载项。管理员可用 `/S` 静默安装、`/dir=路径` 指定目录。安装包没有代码签名，Windows 可能提示“未知发布者”，请先核对文件来源与校验值，再选择继续。
2. 首次打开时创建工作室：填写账户名、网名、密码（至少 12 位），选择界面语言和工作室币种。首位账户是超级管理员。
3. 需要语音时，在助手面板分别点“安装语音识别”“安装语音”。安装会从固定来源下载并逐个校验文件。
4. 数据目录位于 `%APPDATA%\Limet Otus Studio`，卸载程序不会删除它。
5. 业务数据的主密钥保存在该目录的 `vault-key.dpapi` 中，由 Windows 的数据保护接口（DPAPI）加密，**只能在同一台电脑、同一个 Windows 用户下解开**。因此：
   - 直接把数据目录复制到另一台电脑，无法读取其中的业务数据。更换电脑时，在“业务配置 → 数据管理 → 备份与恢复”导出业务备份，在新电脑上导入。
   - 重装系统、重建 Windows 用户，或由管理员强制重置该用户的密码，都可能导致密钥无法解开。请定期导出业务备份，并把备份文件另行保存。

桌面版的本地服务只监听 `127.0.0.1`，局域网中的其他设备无法访问。需要多人协作时请部署服务器版。

## 3. 服务器版部署

### 3.1 准备

1. 一台满足第 1.2 节要求的服务器，系统已更新：

   ```bash
   sudo apt update && sudo apt full-upgrade -y
   sudo reboot
   ```

2. 安装 Docker Engine 与 Compose 插件（按 Docker 官方文档安装）。确认：

   ```bash
   docker --version
   docker compose version
   ```

3. 域名的 A/AAAA 记录指向服务器。证书由 Caddy 自动申请，要求公网能访问服务器的 80 和 443 端口。纯内网部署见第 3.6 节。

4. 只开放必要端口。以 Ubuntu 自带的 ufw 为例：

   ```bash
   sudo ufw default deny incoming
   sudo ufw default allow outgoing
   sudo ufw allow OpenSSH
   sudo ufw allow 80/tcp
   sudo ufw allow 443/tcp
   sudo ufw enable
   ```

   注意：Docker 发布的端口可能绕过 ufw 规则。本模板只发布 80/443，不要在 `compose.yml` 中为数据库、页面或 API 增加 `ports`。

5. SSH 建议使用密钥登录并关闭密码登录，为运维账户启用 sudo，不直接用 root 日常操作。

### 3.2 获取源码

克隆源码仓库并切换到对应版本标签（如 `v3.0.0`），或下载发布页附带的源码压缩包，放到专用目录，例如 `/opt/limet-otus-studio`：

```bash
sudo mkdir -p /opt/limet-otus-studio
sudo chown "$USER" /opt/limet-otus-studio
cd /opt/limet-otus-studio
# 将源码解压或检出到此目录
```

### 3.3 生成密钥并填写配置

```bash
cp cloud/.env.example cloud/.env
chmod 600 cloud/.env
openssl rand -base64 32   # 用作 STUDIO_MASTER_KEY
openssl rand -hex 24      # 用作 STUDIO_DB_PASSWORD
openssl rand -hex 24      # 用作 STUDIO_SETUP_TOKEN
```

用编辑器打开 `cloud/.env`，把三个随机值和域名填进去：

| 变量 | 说明 | 示例格式 |
| --- | --- | --- |
| `STUDIO_DOMAIN` | 对外域名 | `studio.example.com` |
| `STUDIO_ORIGIN` | 与域名一致的 HTTPS 地址，不带路径和结尾斜杠 | `https://studio.example.com` |
| `STUDIO_DB_PASSWORD` | 数据库密码。用十六进制，避免特殊字符破坏连接串 | 48 位十六进制 |
| `STUDIO_MASTER_KEY` | 主密钥，32 字节随机值的 Base64 | 44 个字符 |
| `STUDIO_SETUP_TOKEN` | 首次创建工作室用的一次性令牌 | 48 位十六进制 |
| `STUDIO_AI_ALLOWED_HOSTS`（可选） | 允许使用内网地址或 HTTP 的自托管 AI 主机名，逗号分隔 | `llm.lan` |
| `STUDIO_WEATHER_ALLOWED_HOSTS`（可选） | 允许使用内网地址或 HTTP 的自建天气服务主机名，逗号分隔 | `weather.lan` |

要点：

- **主密钥决定能否读取数据。** 把 `STUDIO_MASTER_KEY` 抄存到与服务器、备份都分开的地方，例如离线的密码管理器。丢失后已有数据无法解密；泄露后应视为数据可能外泄。
- `STUDIO_ORIGIN` 必须与浏览器地址栏中的地址完全一致（协议、域名、端口），否则请求会因来源校验失败被拒绝。
- 每个实例使用各自的随机值，不要复用示例或其他环境的值。
- 不要把 `cloud/.env` 提交到代码仓库，也不要发到聊天或截图中。

### 3.4 启动

```bash
docker compose --env-file cloud/.env -f cloud/compose.yml config --quiet
docker compose --env-file cloud/.env -f cloud/compose.yml up -d --build
docker compose --env-file cloud/.env -f cloud/compose.yml ps
```

第一条命令只检查配置，没有输出表示通过。首次构建需要几分钟。`ps` 中四个服务都应为 `running`，数据库为 `healthy`。

网络结构：

| 服务 | 端口 | 是否对外 |
| --- | --- | --- |
| proxy（Caddy） | 80、443 | 是，唯一入口 |
| web（Next 页面） | 3000 | 否，仅内部网络 |
| api（独立 API） | 38322 | 否，仅内部网络 |
| db（PostgreSQL 17） | 5432 | 否，仅内部网络 |

Caddy 把 `/api/v1/*` 转发给 API，其余转发给页面，并添加以下响应头：`Strict-Transport-Security`（一年，含子域名）、`X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`、`Referrer-Policy: no-referrer`。

### 3.5 首次开通

1. 浏览器打开 `https://studio.example.com`（换成你的域名），确认地址栏显示有效证书。
2. 选择“创建工作室”，填入 `STUDIO_SETUP_TOKEN` 和超级管理员信息。
3. 开通完成后，令牌不能再次使用。可将 `cloud/.env` 中它的值清空（保留 `STUDIO_SETUP_TOKEN=`）并重启 API；令牌为空时，网页端无法再次执行首次开通：

   ```bash
   docker compose --env-file cloud/.env -f cloud/compose.yml up -d api
   ```

4. 在“工作室偏好 → 账户与权限”生成邀请代码，按最小权限给成员分配角色。没有预置账号或默认密码。

验证：

```bash
curl -fsS https://studio.example.com/api/v1/health
docker compose --env-file cloud/.env -f cloud/compose.yml logs --since 10m api web proxy
```

健康接口只说明服务能响应，还应完成一次示例流程：登录、创建订单、前后期工单、确认交付、退出。

### 3.6 内网部署（没有公网域名）

仍须使用 HTTPS。可选方案：

- 使用内网 DNS 名称，并由单位内部的证书机构签发证书；在 `Caddyfile` 中用 `tls <证书> <私钥>` 指定证书文件。
- 使用 Caddy 的内部证书（`tls internal`），并把 Caddy 的根证书安装到每台访问设备的受信任根证书中。

不要改为 HTTP 访问；那样不仅会登录失败，还会让会话和业务数据以明文在网络中传输。

## 4. 软件内的防护措施

下面列出软件自带的机制及部署时需要配合的事项。这些机制降低常见风险，但不能保证没有漏洞。

| 方面 | 软件做了什么 | 部署方需要做什么 |
| --- | --- | --- |
| 传输 | 服务器模式下会话 Cookie 带 `Secure`、`HttpOnly`、`SameSite=Strict` | 必须 HTTPS；保持 Caddy 的 HSTS 头 |
| 来源校验 | 只接受 `STUDIO_ORIGINS` 中的来源；修改请求还须带 CSRF 令牌 | `STUDIO_ORIGIN` 填写准确 |
| 账户 | 密码至少 12 位，以 scrypt 慢哈希保存；会话 12 小时有效，退出即撤销；更改角色会结束该成员的现有会话 | 成员离开时及时停用账户 |
| 开通 | 服务器首次开通须一次性令牌；之后只能凭邀请代码注册，邀请 48 小时有效、仅用一次 | 开通后清除令牌 |
| 权限 | 五种角色、十五个权限点；助手最高只有摄影师权限，不能管理账户、密钥或款项 | 按最小权限分配角色 |
| 限流 | 同一账户登录 15 分钟内最多 10 次；首次开通、注册、AI、语音、CLI 分别限流 | 反向代理保留真实连接，不要在前面加会合并请求的缓存 |
| 数据加密 | 业务数据、AI 服务凭据、对话等以 AES-256-GCM 加密存储，按用途绑定上下文 | 主密钥与备份分开保管 |
| API 密钥 | 按服务单独创建，限定权限与有效期，可随时撤销；复制前须验证密码 | 每个集成单独一把密钥，定期轮换 |
| 外部请求 | AI 服务与天气接口地址不允许指向内网保留地址（分别可用 `STUDIO_AI_ALLOWED_HOSTS`、`STUDIO_WEATHER_ALLOWED_HOSTS` 放行自托管主机）；错误信息不回显密钥 | 只放行确实需要的主机 |
| AI 与隐私 | 发给模型的工具参数去掉备注、性别、成年状态等字段；联网检索不发送客户资料；写操作须人工确认 | 选择可信的模型服务商，了解其数据政策 |
| 审计 | 关键操作写入审计记录，超级管理员可查看最近 200 条 | 定期检查异常操作 |
| 资料留存 | 按交付时间计算保留期，到期提醒、延期审批；清理时删除客户资料与付款凭证截图，只保留脱敏金额记录 | 根据业务和法规要求设置保留期；外部副本另行清理 |
| 响应头 | 接口响应 `Cache-Control: no-store`、`nosniff`、`X-Frame-Options: DENY`、`Referrer-Policy: no-referrer` | —— |
| 桌面端 | 本地服务只监听 127.0.0.1；页面运行在沙箱中，不能直接调用系统接口；麦克风只授予主窗口 | 保持操作系统更新，启用磁盘加密 |

## 5. 服务器运维要求

以下是让服务器版稳定、可控运行的基本要求。软件目前的已知限制见第 10 节。

### 5.1 网络边界

- 防火墙默认拒绝入站，只放行 80/443；SSH 等管理端口只允许固定的运维地址访问，或通过 VPN、云平台的堡垒机进入。
- 限制服务器主动外联：业务需要的只有证书签发、软件更新、所选的 AI 服务与天气服务（默认为 Open-Meteo，可在命令面板“天气”模块改为商业接口或自建服务）。
- 天气授权：Open-Meteo 免费接口仅限非商业用途。用于商业经营时，请自行确认其条款，必要时购买商业接口或部署自建的 Open-Meteo。
- 对外服务前加一层 Web 应用防火墙（WAF）或云平台的防护服务，用于拦截扫描和常见攻击流量。

### 5.2 主机与容器

- 操作系统开启自动更新（`unattended-upgrades`），每月至少检查一次补丁并按需重启。
- Docker、Compose 与基础镜像保持更新；升级时使用 `--build` 重新构建，以获取镜像的修补。
- 安装主机入侵检测与防恶意代码软件，或启用云平台提供的主机防护服务。
- 每季度做一次漏洞扫描，发现的问题记录并跟踪到修复完成。
- SSH 仅允许密钥登录，可加装 fail2ban；运维账户使用 sudo，不直接用 root 日常操作。
- 服务器磁盘启用加密（云盘加密或 LUKS）。

### 5.3 日志与监控

- 保留操作系统、Docker 容器、PostgreSQL、Caddy 与软件审计记录的日志**不少于 6 个月**，集中存放到与业务服务器分开的位置，限制修改权限。
- 对 `https://<你的域名>/api/v1/health` 做外部探测；对磁盘空间、内存、证书到期时间设置告警。
- 日志中可能包含订单号、账户名等信息，分享给他人前先检查并去除。

### 5.4 人员与值守

- 指定一名**运维负责人**，并明确系统管理员、审计员由谁担任。审计员不应由日常操作软件的人兼任，负责定期复核软件审计记录和服务器日志。
- 安排**值守**：工作时间内至少有一名可联系、能处理告警的人员；非工作时间的告警按约定时限响应。把联系人、联系方式与响应时限写成书面安排。
- 人员入职时签署保密协议，按岗位分配最小权限；离职或调岗当天停用软件账户、撤销其 API 密钥和服务器访问权限。
- 每年至少组织一次培训，内容包括口令管理、钓鱼识别、数据处理规范与事件报告。

### 5.5 事件响应

1. 发现异常（告警、可疑登录、数据异常）后，值守人员先记录时间和现象，通知运维负责人。
2. 必要时隔离：停止对外服务（`docker compose ... stop proxy`），保留日志与现场。
3. 评估影响范围：涉及哪些账户、订单与个人信息。
4. 处置：重置受影响账户的密码、撤销 API 密钥；若怀疑主密钥泄露，按备份与恢复流程迁移到新实例。
5. 通知：涉及个人信息泄露时，按所在地法律法规的要求及时通知有关部门和受影响的个人。
6. 复盘：记录原因和改进措施，更新制度。

### 5.6 物理与机房

服务器应放在有门禁、视频监控、防火防水、温湿度控制和备用电源的机房，或选择具备相应资质的云服务商。不要把服务器放在办公室等无人看管的位置。

### 5.7 备份与密钥

- 备份文件加密后再传到异地，例如使用 `age` 或 `gpg`。
- 主密钥离线保存，知悉的人尽量少；备份与主密钥分开存放。

### 5.8 AI 服务

如需完全不向外部发送数据，可接入自托管模型，并在 `STUDIO_AI_ALLOWED_HOSTS` 中放行它的主机名；或者不启用 AI 功能。

## 6. 服务器启用语音识别（可选）

容器只包含识别运行时，不含模型。需要时：

```bash
# 在服务器上下载并校验模型（校验值见 speech/MODEL.json 的 archiveSha256）
cd /tmp
curl -fLO https://github.com/k2-fsa/sherpa-onnx/releases/download/asr-models/sherpa-onnx-sense-voice-zh-en-ja-ko-yue-int8-2024-07-17.tar.bz2
sha256sum sherpa-onnx-sense-voice-zh-en-ja-ko-yue-int8-2024-07-17.tar.bz2
```

核对输出与 `speech/MODEL.json` 中的 `archiveSha256` 一致（大小写不同不影响）后，解出两个文件，放进 API 的数据卷，并在 `compose.yml` 的 `api.environment` 中加入 `STUDIO_SPEECH_MODELS: /var/lib/studio/data/speech-models`：

```bash
mkdir -p speech-models
tar -xjf sherpa-onnx-sense-voice-zh-en-ja-ko-yue-int8-2024-07-17.tar.bz2 --strip-components=1 -C speech-models \
  sherpa-onnx-sense-voice-zh-en-ja-ko-yue-int8-2024-07-17/model.int8.onnx \
  sherpa-onnx-sense-voice-zh-en-ja-ko-yue-int8-2024-07-17/tokens.txt
docker compose --env-file cloud/.env -f cloud/compose.yml cp speech-models api:/var/lib/studio/data/
docker compose --env-file cloud/.env -f cloud/compose.yml up -d api
```

识别原生库需在服务器的 CPU 架构上实际验证。

## 7. 备份与恢复

需要备份的内容：

| 内容 | 位置 |
| --- | --- |
| 数据库 | 卷 `db-data`（建议用 `pg_dump` 导出） |
| API 数据目录 | 卷 `api-data`（留存日志、恢复记录等） |
| Caddy 证书与状态 | 卷 `caddy-data`、`caddy-config` |
| 配置 | `cloud/.env`（含主密钥，单独加密保管） |

数据库导出示例：

```bash
docker compose --env-file cloud/.env -f cloud/compose.yml exec -T db \
  pg_dump -U studio -d studio -Fc > studio-$(date +%Y%m%d).dump
```

- 备份周期和保留期按业务需要确定，并与第 4 节的资料留存设置保持一致：已按留存规则清理的资料，不应长期留在旧备份中。
- 至少每季度在独立环境做一次真实恢复，核对订单、成员、历史快照与主密钥能否对应，并记录耗时。
- 恢复须使用同一个主密钥。

## 8. 升级

1. 先完成第 7 节的备份。
2. 阅读[版本更新说明](版本更新说明.md)，确认是否有不兼容变化。
3. 在单独目录中获取新版本源码，复制原有的 `cloud/.env`。
4. 停止写入（通知成员），然后：

   ```bash
   docker compose --env-file cloud/.env -f cloud/compose.yml up -d --build
   ```

5. 完成第 3.5 节的验证流程。
6. 需要回退时，先停止服务，用升级前的备份恢复数据库，再启动旧版本。不要假定数据库结构可以自动降级。

## 9. 常见问题

| 现象 | 处理 |
| --- | --- |
| 登录后又回到登录页 | 几乎都是没有用 HTTPS 访问，或 `STUDIO_ORIGIN` 与地址栏不一致 |
| 页面打不开 | 核对域名解析、80/443 端口、`docker compose ps` 与 Caddy 日志 |
| 证书申请失败 | 公网 80/443 是否可达，域名是否已指向本机 |
| 接口返回“不受信任的来源” | `STUDIO_ORIGIN` 填写有误，修改后重启 API |
| 首次开通失败 | 核对令牌；已开通的实例不能再次开通 |
| 数据无法读取 | 主密钥与数据库是否来自同一实例 |
| 登录提示过于频繁 | 等待 15 分钟后重试，并检查是否有人在尝试猜测密码 |
| 语音不可用 | 桌面版在助手面板安装；服务器版见第 6 节 |

## 10. 已知限制

以下是软件目前的限制，部署时可以用制度或外部措施弥补，也是后续版本的改进方向：

| 限制 | 弥补方式 |
| --- | --- |
| 口令只要求长度（12 位以上），没有复杂度校验 | 制定口令制度并告知成员，定期抽查 |
| 没有空闲超时自动退出（会话 12 小时到期） | 要求成员离开时退出或锁屏；共享电脑上不保留登录 |
| 没有双因素认证 | 需要时由反向代理或单点登录系统提供 |
| 没有独立的审计员角色，超级管理员与管理员都能查看审计记录 | 由不参与日常操作的人担任审计员，定期从数据库导出审计记录交其复核 |
| 审计记录界面只显示最近 200 条，不能导出 | 运维人员定期导出数据库中的 `audit` 表并归档 |
| 不含入侵检测、防恶意代码与集中日志 | 使用云平台或主机层面的相应产品 |
| 安装包没有代码签名 | 从可信渠道获取并核对校验值 |
| 删除订单后，数据库中的历史版本与已有备份仍保留副本，直到留存清理或备份到期 | 客户要求删除资料时，同时清理相关备份；必要时缩短备份保留期 |
